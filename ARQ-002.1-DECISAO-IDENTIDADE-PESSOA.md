# ARQ-002.1 — Decisão Arquitetural de Identidade da Pessoa (somente diagnóstico)

> Realizado em 2026-07-30, resolvendo a pergunta em aberto deixada pelo ARQ-002. **Nenhum
> código foi alterado.** Este documento avalia as duas alternativas propostas — não parte de
> nenhuma delas como resposta certa — e corrige, com evidência nova, uma suposição desta sessão
> que era imprecisa.

---

## 0. Correção de evidência antes de decidir

Ao revisar o "Caso 1" (coordenador/tutor que ainda não é participante), esta sessão tinha uma
suposição em aberto: a memória do projeto registra que "tutores também são participantes", o
que parecia contradizer o caso. **Fui conferir no código antes de aceitar qualquer um dos dois
lados** — e o código resolve a dúvida de forma inequívoca, a favor do argumento do usuário:

```js
// ATIVACAO-01: criação de Pequeno Grupo pelo Tutor autenticado (allowlist)
async function confirmarCriarPg(nomeTutor) {
  ...
  g.tutor = nomeTutor;        // ← string solta, gravada AQUI
  await saveGrupos();
  ...
}
```
*(index.html:3169-3190)*

No momento em que um Tutor cria um Pequeno Grupo, `g.tutor` recebe uma **string de nome**
diretamente — **nenhum registro em `g.participantes[]` é criado nesse fluxo**, logo **nenhum
`memberId` existe para esse Tutor neste PG** até (e se) ele, separadamente, também se inscrever
como participante. A afirmação da memória do projeto ("tutores também são participantes") é
verdadeira como fato observado em produção (os 4 tutores atuais aparentemente também participam
de algum PG), mas **não é uma garantia estrutural do código** — é comportamento que pode não se
repetir com o próximo tutor, ou pode não valer no momento exato da criação do grupo. **O "Caso
1" do usuário está correto, com evidência direta**, não é uma preocupação hipotética.

Isso muda o peso da decisão: não é só "e se um dia existir um Administrador" (Caso 2, ainda
hipotético) — é um caso **já presente hoje**, na função mais básica do sistema (criar um PG).

---

## 1. As duas alternativas, reafirmadas

**Modelo A** — `Pessoa` ganha `personId` próprio; Participante/Tutor/Coordenador tornam-se
papéis/relacionamentos que referenciam esse id.

**Modelo B** — `memberId` (já existente no Participante) é promovido a identificador universal
de Pessoa.

---

## 2. Avaliação pelos 10 critérios pedidos

### 1. Domínio do sistema
`memberId` nasce e vive hoje **dentro de** `g.participantes[]` — não existe como registro
independente em lugar nenhum do código (confirmado: nenhuma coleção/array de nível superior
guarda participantes fora do contexto de um PG específico). "Promover" esse campo a identidade
universal exigiria, na prática, **extrair um registro para fora do PG de qualquer forma** — o
que é, estruturalmente, construir o Modelo A e só chamar o id de `memberId` em vez de `personId`.
**Não são duas arquiteturas finais diferentes — são a mesma arquitetura final com um nome
diferente, mais um caminho (B) que tenta adiar a extração e falha em fazê-lo de verdade.**

### 2. Pessoas com papel mas sem participação
Confirmado na seção 0: já ocorre hoje (Tutor recém-criando um PG). Modelo B não tem onde
guardar a identidade desse Tutor até ele (talvez nunca) virar participante de algum PG. Modelo A
resolve nativamente — `Pessoa` existe a partir do primeiro contato (login por allowlist), antes
de qualquer participação.

### 3. Autenticação futura (ARQ-003)
Qualquer mecanismo de autenticação (mesmo Firebase Anônimo) precisa de **um lugar para gravar o
vínculo entre a credencial e a pessoa**, independente de ela estar hoje dentro de algum PG. Um
registro `Pessoa` central é esse lugar natural. Sob o Modelo B, esse vínculo teria que apontar
para dentro de um array aninhado de um PG específico — frágil e circular (o que acontece se a
pessoa sai do PG?).

### 4. Firebase Auth
Importante deixar explícito, porque nenhuma das duas alternativas resolve isso sozinha: o UID
que o Firebase Authentication gera (mesmo anônimo) é **um terceiro identificador**, não o mesmo
que `personId`/`memberId`. A pergunta certa não é "qual dos dois vira o UID do Firebase" — é
"`Pessoa.authUid` aponta para o UID do Firebase, e `Pessoa.personId` é a chave estável que o
resto do sistema referencia" (o UID pode até mudar — ex.: troca de método de login — sem quebrar
nenhuma referência interna, se ninguém além da própria `Pessoa` guardar o UID diretamente).
**Isso só é possível com um registro `Pessoa` central — de novo, aponta para o Modelo A.**

### 5. Permissões
Permissão de servidor (`request.auth.uid` nas regras do Firestore) precisa checar "este UID
corresponde a uma Pessoa com o papel X" — uma consulta a um registro central de Pessoa é mais
simples e auditável do que varrer `g.participantes[]` de 50 grupos procurando um `memberId`.

### 6. Auditoria
Um evento de auditoria ("quem fez o quê") deveria apontar para a Pessoa, não para uma
participação específica — a mesma pessoa pode agir como Tutor do PG 3 numa ação e como
participante comum do PG 9 noutra; um log que aponta só para `memberId` (Modelo B, id nascido
dentro de um PG) fragmenta o histórico de uma pessoa em pedaços por grupo. `personId` central
(Modelo A) mantém o histórico de uma pessoa unificado, mesmo atravessando papéis e grupos.

### 7. Histórico
Idem ao item 6 — "Pessoa saiu do PG 3 e voltou 2 meses depois" só é uma frase com sentido se
existir um identificador que sobrevive à saída. Hoje, sair de um PG aciona o tombstone do
**Participante**, não de uma Pessoa — reforça que Participante é uma **relação com estado**
(entrou/saiu), não a identidade em si. Isso é exatamente a modelagem `ParticipacaoPG` proposta
pelo usuário, e ela só faz sentido se houver uma `Pessoa` estável por trás.

### 8. Migração dos dados existentes
Aqui está a única vantagem real e honesta do Modelo B: **custo de migração menor no primeiro
momento**, porque não introduz uma coleção nova. Mas essa vantagem é ilusória à luz do item 1 —
qualquer implementação séria de "memberId universal" acaba precisando construir a mesma extração
de registro que o Modelo A já assume de saída. A diferença real de custo entre os dois é
pequena; a diferença de correção estrutural não é. (Plano conceitual de migração na seção 4.)

### 9. Escalabilidade institucional
O app já é usado por dezenas de PGs e a expectativa (roadmap RC4.8.4, Painel ADV-E) é crescer
para consolidação institucional cross-PG. Um modelo que trata "pessoa" como algo que só existe
dentro de um PG não escala para relatórios institucionais que precisam somar uma pessoa só uma
vez mesmo que ela toque múltiplos PGs/papéis — mesma classe de problema que a Cobertura Setorial
já resolveu para "setor" (ADR-001) evitando fragmentação. Faz sentido aplicar o mesmo padrão já
validado no projeto (identidade central + referências por id) à Pessoa.

### 10. Manutenção futura
Modelo A tem um custo perene pequeno (mais uma entidade para explicar/manter), mas remove a
necessidade de racionalizar, para sempre, por que "memberId" (nome que sugere "membro de algo")
representa também um Administrador que nunca participou de nada. Nomes que mentem sobre o que
representam são a fonte mais comum de confusão em manutenção de longo prazo.

---

## 3. Decisão Recomendada

**Modelo A — `Pessoa` ganha `personId` próprio.**

Concordo com a recomendação do usuário, com uma justificativa mais forte do que a inicialmente
proposta: não é só que o Modelo B "não seria ideal" — é que **o Modelo B, implementado de forma
que resolva de verdade os problemas dos critérios 2-9 acima, deixa de ser o Modelo B e vira o
Modelo A**. A única forma de "promover memberId" sem construir um registro central de Pessoa é
não resolver os casos que motivaram esta decisão — o que devolveria o sistema ao mesmo ponto em
que o ARQ-002 o encontrou.

---

## 4. Impactos

- **`Pessoa`** vira a única entidade com identidade permanente: `{personId, nome, whatsapp,
  status, authUid (quando existir), papéis[]}`.
- **`Participante`** deixa de carregar a identidade em si — vira **`ParticipacaoPG`**:
  `{personId, pgId, papel, dataEntrada, dataSaida, status}` — o "papel" (tutor/coordenador/
  colaborador/amigo/membro) migra para ser um atributo da participação, não da pessoa (uma
  pessoa pode ter papéis diferentes em PGs diferentes, ou nenhum papel específico além de
  "participante").
- **`g.tutor`/`g.coordenador`** passam a guardar `personId` (`g.tutorPersonId`); o nome exibido
  na tela é sempre buscado a partir da `Pessoa`, nunca congelado como string.
- **`compParceiro[]`** passa a guardar `personId` em vez de `{nome, ts}`.
- **`gratidao.autor`** passa a guardar `personId` em vez de nome — abre caminho natural para
  "minhas gratidões" sem varrer todos os PGs.
- **Convite** já está correto (`deId` = `memberId` hoje) — só precisa passar a apontar para
  `personId` em vez de `memberId`, troca direta.

## 5. Riscos

- **Maior superfície de mudança que o Modelo B** — toca mais pontos do código (todos os "por
  nome" catalogados no ARQ-002, Achado 3). Mitigação natural: como o ARQ-003 (Identidade) já ia
  precisar tocar esses mesmos pontos de qualquer forma para adicionar autenticação, não há
  trabalho duplicado — é o mesmo esforço, só ordenado corretamente.
- **Janela de convivência dos dois modelos durante a migração** (ver seção 6) é, por natureza,
  o mesmo tipo de risco já visto no projeto (AUD-001: campo novo introduzido, mas nem toda
  leitura/escrita atualizada ao mesmo tempo) — mitigável com o mesmo checklist já recomendado no
  ARQ-001 (write + read + merge + allowlist), desta vez aplicado à introdução de `personId`.
- **Custo de explicar mais um conceito** a um time pequeno e não-técnico — real, mas menor que o
  custo de manter uma ambiguidade estrutural indefinidamente.

## 6. Plano Conceitual de Migração (sem código, só sequência)

1. **Criar o registro `Pessoa`** — para cada `memberId` já existente, gerar um `personId` e uma
   entrada `Pessoa` correspondente (nome, whatsapp, papéis observados). Nesta etapa, `memberId`
   não desaparece — passa a ser tratado como o identificador da `ParticipacaoPG`, não da Pessoa.
2. **Resolver os "órfãos"** — tutores/coordenadores que só existem hoje como string em
   `g.tutor`/`g.coordenador` sem `memberId` associado (o caso confirmado na seção 0) precisam de
   uma `Pessoa` criada a partir só do nome — sem forma automática de saber se essa string
   corresponde a uma `Pessoa` já criada por outro caminho (mesmo risco de duplicação por nome já
   existente hoje, RC-REST-02) até haver confirmação humana ou reautenticação.
3. **Migrar as referências por nome** — `compParceiro`, `gratidao.autor`, `g.tutor`/
   `g.coordenador` passam a apontar para `personId`, mantendo o nome só como cache de exibição
   (nunca como chave).
4. **Só então** iniciar o ARQ-003 (Identidade/Autenticação) — a autenticação vincula uma
   credencial provável (WhatsApp confirmado, Firebase Auth) a um `personId` já existente, em vez
   de a um `memberId` que significa "participação", não "pessoa".

---

## 7. Critério para seguir

Esta decisão fecha a pergunta em aberto do ARQ-002. O ARQ-003 pode agora ser desenhado em cima
de uma pergunta mais precisa, como o próprio usuário nomeou: **"como o sistema comprova quem é
uma Pessoa que já possui identidade conceitualmente definida?"** — não mais "que id usar".

**Esta auditoria é exclusivamente diagnóstica — nenhum código foi escrito, corrigido ou
refatorado.**
