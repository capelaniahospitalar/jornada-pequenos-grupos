# ARQ-004.1 — Estratégia de Migração do Modelo de Persistência (somente diagnóstico/projeto)

> Realizado em 2026-07-30, respondendo ao destino já aceito no ARQ-004 (modelo híbrido orientado
> a domínio: `/pessoas`, `/pequenos_grupos`, `/participacoes`, `/setores`, `/pg_setores`,
> `/atividades`, `/convites`, `/auditoria`). **Nenhum código foi alterado, nenhuma coleção nova
> foi criada.** Este documento responde só à pergunta "como chegar lá sem quebrar nada" — o
> "para onde" já foi decidido no ARQ-004.

---

## 0. Duas provas de que este projeto já sabe fazer este tipo de migração

Antes de desenhar algo novo, vale registrar: **este exato tipo de mudança — trocar a forma como
um dado é guardado, com dado real de produção, sem parar o app — já foi feito aqui, duas
vezes, com sucesso documentado.** A estratégia abaixo não inventa um método novo; generaliza o
que já funcionou.

**Precedente 1 — `migrarSetoresParaMestre()` (RC4.8.2A, index.html:5259-5284):** quando o Setor
deixou de viver embutido em cada PG e passou a ter um Cadastro Mestre próprio (o mesmo tipo de
mudança de forma que o ARQ-004 propõe agora, só que em escala menor), a migração foi:
**idempotente** (`if (typeof g.setores[0] !== 'object') return` — se já migrado, não faz nada),
**disparada sozinha a cada sincronização** (chamada dentro de `salvarFbConfig`/
`syncFromFirebase`, sem exigir ação do usuário), e **grava pelo mesmo caminho de escrita normal**
(`saveGrupos()` — nenhum código especial de "modo migração"). Zero downtime, zero tela de
migração, zero perda de atribuição de setor por participante (confirmado no `CHANGELOG.md`).

**Precedente 2 — IMD v2 (RC3.5.3 → RC3.5.5, `ARCHITECTURE.md`):** quando o motor de cálculo do
IMD foi trocado (`getPgIMD` → `getPgIMDv2`), o caminho foi: motor novo convive com o antigo atrás
de uma *feature flag* (`FB_FLAGS.imdV2Diagnostico`) → painel de diagnóstico mostra os dois lado a
lado para comparação humana → só depois de validado com dado real de produção, a interface corta
para o motor novo (`FB_FLAGS.imdV2 = false` continua existindo como **rollback de um clique**,
sem precisar reconstruir nada) → motor antigo é removido só depois, numa RC futura (RC3.6).

**Esta estratégia é a generalização desses dois precedentes** para uma mudança maior — troca de
`FB_FLAGS` fica sendo a mesma ferramenta; o que muda é a escala (5+ entidades, não 1 setor ou 1
motor de cálculo).

---

## 1. Fase 0 (adicionada por esta auditoria) — Rede de segurança antes de começar

O ARQ-001 já registrou que o projeto **não tem nenhum mecanismo de backup** (Pilar 3,
Recuperação). Começar a maior migração estrutural já proposta nesta série sem um retrato do
estado atual seria repetir o mesmo risco que já causou os dois incidentes reais do Grupo 1/22.

**Antes de qualquer linha de código da migração:** exportar manualmente o documento único atual
(`jdpg/grupos`, via console do Firebase ou uma leitura simples) para um arquivo, guardado fora do
Firestore. Não é a solução de backup definitiva (isso é assunto do ARQ-005) — é o mínimo
responsável antes de mexer na fundação de tudo. Custo: minutos. Benefício: se algo na Fase 1-2
sair diferente do esperado, existe um ponto de retorno conhecido.

## 2. As seis perguntas

### 1. Como migrar sem parar o aplicativo?

Réplica direta do Precedente 1: cada nova coleção é populada por uma função **idempotente**,
disparada automaticamente a cada sincronização (mesmo ponto em que `migrarSetoresParaMestre()`
já é chamada hoje), gated por uma `FB_FLAG` nova (ex.: `FB_FLAGS.pessoaModelo`). Enquanto a flag
estiver desligada, a função só **cria e popula** as coleções novas — nenhuma tela, nenhum
comportamento visível muda. O aplicativo nunca fica fora do ar porque a migração não é um evento
único e coordenado — é um efeito colateral silencioso de cada sincronização normal que já
acontece.

### 2. Como manter dados antigos funcionando?

O documento único (`jdpg/grupos`) **continua sendo escrito normalmente durante toda a Fase 1 a
3** — nada é removido, nada para de funcionar. Todo o código de leitura atual (`fbReadDoc`,
`PEQUENOS_GRUPOS`, etc.) segue intocado até a Fase 2 decidir, **entidade por entidade**, trocar a
fonte de leitura. Isso significa que, a qualquer momento durante a migração, desligar a flag
nova devolve o app exatamente ao comportamento de hoje.

### 3. Como validar que nada foi perdido?

Réplica direta do Precedente 2: um **painel de diagnóstico comparativo**, visível só para Tutor/
Coordenador (mesmo portão do Ranking), mostrando, por entidade migrada:

| Comparação | Modelo antigo | Modelo novo |
|---|---|---|
| Nº total de pessoas distintas | (contagem por nome único — aproximada, é o próprio problema que motivou o ARQ-002) | Nº de documentos em `/pessoas` |
| Nº de participações ativas | Soma de `g.participantes` sem tombstone, todos os PGs | Nº de documentos em `/participacoes` com `status:'ativo'` |
| Nº de setores | `SETORES_MESTRE.length` | Nº de documentos em `/setores` |
| Participantes por PG (amostra) | `g.participantes.length` de cada PG | Contagem de `/participacoes` filtradas por `pgId` |

Diferença encontrada = alerta para decisão humana, nunca resolução automática silenciosa (mesmo
princípio já usado no projeto: nunca inventar número onde há dúvida, ver `ARCHITECTURE.md`,
IMD). Como o projeto não tem testes automatizados (ARQ-001), **a validação real acontece com
dado de produção mesmo** — mas de forma não-destrutiva, porque o documento antigo nunca é
desligado antes da Fase 4.

### 4. Qual entidade migrar primeiro?

Refinamento sobre a proposta original: dentro da própria "Fase 1", a ordem entre as 4 entidades
importa, porque há dependência entre elas:

```
1º Pessoa           (nada mais referencia nada até isso existir)
2º Participação     (referencia Pessoa + PG — precisa que Pessoa já exista)
3º Pequeno Grupo    (metadados; tutorPersonId/coordenadorPersonId dependem de Pessoa)
4º Setor            (já é o de menor esforço de extração — ADR-001 já isolou o conceito;
                      pode inclusive andar em paralelo com os 3 acima, sem dependência real)
```

Convites/Mural ficam para depois — maior volume de registros, mais telas tocam neles, e nenhuma
das duas bloqueia a fundação de Identidade que motivou todo este ARQ.

### 5. Como fazer rollback?

Enquanto a Fase 4 não acontecer, rollback é **instantâneo e gratuito**: desligar a `FB_FLAG`
correspondente devolve leitura e escrita ao documento único, sem precisar desfazer nem
reconstruir nenhum dado — porque o documento único nunca parou de receber as escritas normais.
Rollback só deixa de ser trivial **depois** da Fase 4 (documento antigo desligado) — por isso a
recomendação é tratar a Fase 4 como a decisão mais lenta e mais observada de toda a migração
(ver seção 3, "Critério de corte").

### 6. Como conviver temporariamente com dois modelos?

Regra única para evitar o pior cenário (inconsistência parcial disfarçada de sucesso): **escrita
dupla sempre grava nos dois modelos ao mesmo tempo** (Fase 1-3); **leitura nunca mistura fontes
para a mesma entidade na mesma tela** — cada entidade lê 100% do modelo antigo OU 100% do modelo
novo, controlado por uma única flag por entidade, nunca uma mistura "peguei um campo de cada".

## 3. Sequência de Fases (refinada)

```
Fase 0 — Snapshot manual de segurança do documento único (uma vez, antes de tudo)
Fase 1 — Criar + popular novo modelo (Pessoa → Participação → PG → Setor), escrita dupla,
         leitura 100% do modelo antigo ainda. Flags desligadas por padrão.
Fase 2 — Migrar LEITURA, entidade por entidade, atrás de flag — painel de diagnóstico ativo
         o tempo todo enquanto a flag daquela entidade estiver ligada.
Fase 3 — Migrar ESCRITA "de origem" — ações do usuário passam a escrever primeiro no modelo
         novo; escrita no documento antigo continua, agora como espelho de segurança
         (invertido em relação à Fase 1).
Fase 4 — Desligar o documento único, só depois de um período de observação equivalente ao já
         usado no IMD v2 (Fase de Implantação, 60 dias) sem nenhuma divergência não-explicada
         no painel de diagnóstico.
```

**Critério de corte da Fase 4 (mesmo espírito do critério já usado para o IMD v2 — condição
verificável, não impressão subjetiva):** só avançar quando, simultaneamente, (a) todas as
entidades tiverem passado por pelo menos 60 dias de escrita dupla sem divergência, (b) o painel
de diagnóstico não apontar nenhuma discrepância pendente de explicação, e (c) pelo menos um
ciclo completo de "troca de aparelho"/"recuperação de identidade" real (não simulado) já tiver
sido observado com sucesso sob o modelo novo.

---

## 4. Ponto técnico que este ARQ-004.1 precisa deixar explícito (decisão para quando a
    implementação começar, não agora)

O acesso ao Firestore hoje é **REST puro, hand-rolled**, contra um único caminho de documento
conhecido (`fbReadDoc`/`fbWriteGrupos`, `.../documents/jdpg/grupos`). Coleções com múltiplos
documentos e consultas (`where personId ==`, `where pgId ==`) exigem, na implementação, uma de
duas rotas: (a) usar o endpoint de consulta do Firestore via REST (`:runQuery`, mais verboso que
um GET simples), ou (b) adotar o SDK do Firestore (possível sem build step, via tag `<script>`,
mas é a primeira dependência externa real que o projeto passaria a ter). **Esta decisão não
precisa ser tomada agora** — é um ponto em aberto sinalizado para quando a Fase 1 for de fato
implementada, não uma pergunta conceitual que trava este documento.

## Riscos

| Risco | Mitigação |
|---|---|
| Escrita dupla ter um bug que só afeta um dos dois modelos, sem ninguém perceber a tempo | Painel de diagnóstico (pergunta 3) ativo desde o primeiro dia da Fase 1, não só na Fase 2 |
| Pressa em avançar a Fase 4 por impaciência, antes do critério de corte | Mesmo risco já identificado e resolvido pelo projeto para o IMD v2 ("não ajustar por reação a resultado inicial") — critério objetivo definido agora, seção 3, não decidido no calor do momento |
| Custo/complexidade de consultas por coleção (ponto técnico, seção 4) subestimado | Sinalizado explicitamente como decisão de implementação em aberto, não escondido dentro de uma fase |

## Recomendação Final

Aprovar a sequência Fase 0-4 acima, com a ordem interna Pessoa → Participação → PG → Setor
dentro da Fase 1. Nenhuma implementação começa nesta série ARQ — esta é a última peça de
planejamento antes de a migração poder, um dia, ser codificada. Sugiro que a Fase 0 (snapshot de
segurança) seja feita **assim que você aprovar este documento**, independente de quando a
implementação de fato começar — é barata, reversível, e já fecha uma lacuna que o ARQ-001 apontou
como risco alto (ausência total de backup) com o menor esforço possível.

**Este documento é exclusivamente diagnóstico/de projeto — nenhum código foi escrito, nenhuma
coleção nova foi criada, nenhuma migração foi executada.**
